# 操作确认台「双入口」差异分析

- 日期：2026-09-22
- 背景：用户提出「工作台已有确认台且稳定，想彻底取消电脑侧弹出的操作确认台」，前提是「工作台效果等同于电脑的」。
- 本文结论：**工作台目前不等同于电脑确认台，它是电脑确认台的子集**。取消前需先补齐 3 处能力缺口，否则是净功能损失。
- 关联：ADR-0029（买入手数分档）、ADR-0031（停用桌面确认台 GUI）

---

## 一、结论摘要

| 判断 | 结论 |
|---|---|
| 两者是否同源？ | **是**，读同一批 JSON（`/Users/williamli/Work/reports/pending_*_confirm_*.json`） |
| 工作台是否等同电脑？ | **否**。工作台只覆盖「买入确认」，且缺 3 项安全校验 |
| 能否现在就彻底取消电脑确认台？ | **不建议**。会丢掉「卖出确认」入口 |
| 用户观察「电脑的没手数」是否准确？ | **不准确（已过期）**。手数是 2026-09-21 13:51（ADR-0029）加的，此前确实没有 |

## 二、有三个「弹出」表面，不是两个

| # | 表面 | 实现 | 触发方式 | 状态 |
|---|---|---|---|---|
| ① | 只读操作闪卡 | `popup_gui.py`（Tk，只读） | 由 `market_scheduler.py` 时段运行内 `open_report_in_textedit()` 拉起 | **仍在自动弹** |
| ② | 桌面交互确认台 | `confirm_gui.py`（Tk，可交互） | 原由 `launch_confirm_gui()` 拉起 | **2026-09-22 已停用**（ADR-0031） |
| ③ | 工作台操作确认台 | `templates/workbench.html` + `app.py` | 页面存活时 `setInterval(pollConfirm, 60000)` 轮询 | **唯一交互入口** |

> 「电脑自己弹出的确认框」= ②；用户平时看到的「电脑弹框」也可能是 ①（只读闪卡，长得像但只能看）。

**没有**独立的「弹出确认框定时任务」。② 是被 4 个 market-advisor 时段运行（09:25/11:40/13:40/14:40）内部拉起的，取消它 = 改 scheduler 代码（已完成），不是停某个 automation。

### 写库链路细节

- `confirm_gui.py` 提交 → 改 JSON → `subprocess.run([PYTHON_BIN, MAIN_SCRIPT, "confirm", "--now"])`（L429）→ **当次立即落库**
- 工作台提交 → `POST /api/confirm/buy` → 只改 JSON（+ `portfolio.add_position`）→ **不落库**
- 15:00 落库依赖：`_spawn_deadline_confirm()`（L1832）在**任一买入时段**运行时挂 detached 子进程 `market_scheduler.py confirm`（L3862-3867 → `_wait_until_deadline("15:00")` → `run_pending_confirmations()`），用 `.confirm_spawned_<YYYYMMDD>` 日期锁保证当日只挂一次
- **无 15:00 的 launchd/plist 备份作业**（`~/Library/LaunchAgents/` 内无 confirm 相关 plist）。源码注释提到的「plist 15:00 备份触发」实际不存在 → 单点依赖那个 detached 子进程

## 五、关键校正：关于「没手数」

用户认为「电脑弹出的操作确认台还是旧的逻辑没带手数的」。核实结果：

| 项 | 结论 |
|---|---|
| `confirm_gui.py` 是否显示手数 | **显示**，且可编辑。`L240-241`：`sug_txt = f"建议 {sug}手≈¥{px*_to_shares(sug)/10000:.1f}万 ｜ "` |
| 数据里是否有手数 | **有**。实测 `pending_buy_confirm_1340_2026-09-22.json` → `suggest_lots: 68` |
| 只读闪卡是否显示手数 | **显示**。实测 `intraday_alert_1340.txt` → `买 瑞康医药(sz002589) 68手` |
| 唯一「无手数」的代码路径 | `_fmt_action`（L3024）当 `buy_shares == 0` 时走 `买 X — <note>` 分支，不输出手数 |

**判定**：手数能力是 **2026-09-21 13:51 随 ADR-0029 一起加入的**（同时改了 `market_scheduler.py` 与 `confirm_gui.py`，见 `market_scheduler.py.bak_20260921_sentiment_lots`）。用户观察到的「没手数」应来自 **09-21 之前**的版本。

> 因此「取消桌面版」的理由不能是「它没手数」——它现在也有。真正的理由只能是「单入口更干净」（ADR-0031 的论据）。

## 六、真实差距（决定能否「彻底取消」）

| 缺口 | 内容 | 后果 | 现在是否暴露 |
|---|---|---|---|
| **G1 · 卖出无 UI（致命）** | 工作台 `app.py:343` 只 glob `pending_buy_confirm_*`，全项目 `actual_sell` / `pending_sell` 引用数 = **0** | 10:40 派出的卖出建议**无任何界面可确认** | 未暴露（50万库连续多日 0 持仓 → 无卖出单） |
| **G2 · 写库时点不同** | 工作台只改 JSON，靠 15:00 detached 子进程落库 | 若某日无任何买入时段成功跑（应用未启动），子进程不会挂 → 工作台确认的**永远进不了库** | 今日未暴露（`.confirm_spawned_20260922` 已于 10:12 创建） |
| **G3 · 缺 3 项安全校验** | 见上表：卖出超持仓、卖满清零股、买入超额现金 | 可派出「现金不够 / 卖超持仓」的无效单 | 逻辑上恒在 |
| **G4 · 弹窗到达性** | 工作台依赖 `setInterval` 轮询，页面关着就不弹 | 人不在电脑前/没开页面 → **完全无提示** | 恒在（可接受：闪卡仍在弹） |

## 七、建议方案

> **【2026-09-22 更新】方案 A 已落地（ADR-0032）**：工作台补齐卖出确认 + 立即写库 + 三项校验，并新增 15:00 launchd 兜底作业（C 一并完成）。实施中还查明并修复了一个比缺口本身更严重的问题 —— 工作台旧实现抢先写 `status=confirmed`，导致写库流程判定"已确认"只改名不写库，**用户确认的买入永远进不了回测库**（桌面确认台因从不写 status 字段而幸免）。详见 ADR-0032。
> 下表保留为决策时的原始选项。

| 方案 | 动作 | 适用 |
|---|---|---|
| **A · 补齐后收敛（已采纳 ✅）** | 工作台加卖出确认（`/api/confirm/sell` + 前端 sell 区）；工作台确认后调 `confirm --now` 立即落库；补 3 项校验；再彻底移除 `confirm_gui.py` | 想真正实现单入口 |
| B · 部分保留 | 维持现状，但 `confirm_gui.py` 保留为**仅卖出**入口（改 `launch_confirm_gui()` 只扫 `pending_sell_confirm_*`），买入完全归工作台 | 最小改动、零风险 |
| C · 加保险不删（已随 A 完成 ✅） | 新增 15:00 launchd 作业跑 `market_scheduler.py confirm`（补上源码注释里承诺但不存在的备份触发），先把 G2 的单点依赖消掉 | 独立于 A/B 都该做 |
