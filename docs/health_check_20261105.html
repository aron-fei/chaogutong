P0 必须立刻处理（2 项）

P0-1 远程访问密钥被明文回显在 403 页面，门禁形同虚设

现象：未授权访问 http://<本机IP>:8765/ 时，服务返回的 403 页面把 ACCESS_KEY 直接拼进 HTML 告诉来访者。
证据：app.py:84-85 —— return ("<h3>访问受限</h3><p>请使用带访问密钥的完整地址打开：<code>http://<电脑IP>:8765/?k=" + ACCESS_KEY + "</code></p>", 403)；密钥存于 data/access_key.json（实测 12 字符）。
影响：局域网内任何人打开首页即得密钥，随后可调用全部写操作接口 —— POST /api/confirm/buy（确认买单并触发写库）、POST /api/portfolio（增改删持仓）、POST /api/fut_advisor（改资金参数/记盈亏）。config.HOST=0.0.0.0 实测监听 *:8765，风险可达。
根因：把「提示用户如何找密钥」误实现成「直接把密钥发给未认证者」。
建议：403 页面只提示「请向管理员获取带密钥的地址」，绝不回显密钥；密钥改为仅从本机文件 / 启动日志查看。可顺手把 app.py:80 的 cookie 明文比较 == 换成 secrets.compare_digest（与 ?k= 分支一致）。
return ("<h3>访问受限</h3><p>请向管理员获取带访问密钥的完整地址（/?k=…）后重试。</p>", 403)

P1 高优先（5 项）

P1-1 两个复盘接口稳定 11–13 秒同步阻塞，且无缓存、无异常兜底

实测：/api/review 两次 11746 / 11933 ms；/api/daily_review 两次 11534 / 13160 ms（非冷启动，稳定慢）。对照：/api/dashboard 10–16 ms、/api/review_deep 384–410 ms、/api/bottom_surge 缓存命中 11–19 ms。
证据：app.py:366 / :408 直接 return jsonify(review.review()) / review.daily_review(md, adv)；review.py 内 kline()、live_quote() 为同步 requests.get 且按天/按股循环。
影响：Flask threaded=True 暂不至于整体卡死，但前端 5 秒轮询 + 多 tab 并发会持续占用工作线程；两接口也没有 try/except，一旦上游异常直接 500 拖垮该 tab（其余接口都有兜底，这两个是例外）。
建议：仿照 bottom_radar 的「TTL 缓存 + 后台刷新 + stale 标记」模式，复盘结果按日缓存（盘中可 60–120s），请求只读缓存；补 try/except 兜底返回结构化 error。

P1-2 指数 MA20/MA30 链路实质失效，且每 5 秒无效重试刷屏

现象：服务日志每轮刷新都打印 [MA] 均线拉取失败: JSONDecodeError: Expecting value: line 1 column 1；dashboard 中 6 个指数的 ma20/ma30 长期为空。
证据：data_fetcher.py:309-328 _refresh_index_ma() 调腾讯 fqkline 日K端点，异常时只打印、不更新 _index_ma_at 也不做退避；:297 的 1 小时缓存判断因此永远成立 → 每轮重试。外层 :299-300 还有一层 except: pass。
影响：①「破 30 日线进防守」这一防守维度实际不生效；②日志被无效重试淹没；③这正是首板雷达只能用「日内双 EMA 代理」而无法用真实 MA5/10/20 的同一根因。
建议：失败时也推进 _index_ma_at（退避到 30–60 分钟）并降级打印；同步评估替换日K源（东财 stock_zh_index_daily / akshare 指数日线），替换后可同时把首板雷达的均线条件从 EMA 代理升级为真实日均线。

P1-3 指数新鲜度戳恒为 null

证据：data_fetcher.py:224-227 初始化了 last_update["indices"] = None，但全文件仅对 concepts/sectors/pools/full 赋值；fetch_indices()（:271-307）成功时只写 self.indices = out，从不更新时间戳。dashboard 实测 last_update.indices = null，其余四项均为 13:24 左右。
影响：指数行情其实在正常刷新（日志「指数 ok」每轮可见），但前端与运维都无法判断其新鲜度，属于「看起来像坏了」的假故障，也会掩盖真实故障。
建议：在 if out: 块内补 self.last_update["indices"] = datetime.now()（一行修复）。

P1-4 30 处 except Exception: pass，违反交付铁律

分布：review_deep 5、review_gate 5、app 4、data_fetcher 3、futures_strategy 3、advisor 2、bottom_surge 2、review 2、watchlist 2、position_watch 1、theme_arb 1。
核心链路命中：app.py:670（闸门状态）、position_watch.py:969（可用现金）、review_gate.py:236/243/768/804/844（复盘闸门判定与幂等）、data_fetcher.py:299（MA 重试）。
影响：异常被静默吞掉，故障表现为「数据悄悄不对但无任何日志」，与你在 vault 里记的血泪史（弹窗环节 except:pass 吞掉全部异常）完全同类。
建议：至少给核心链路的 10 处补 print(f"[{模块}] 取数失败: {type(e).__name__}: {e}")，并考虑统一收敛成一个 _safe(fn, tag) 工具；清理型（如 shutil.rmtree）可保留但注明原因。

P1-5 零自动化测试，25 个模块无回归保护

证据：项目内无 tests/、无 test_*.py；仅 review_gate.py 与 suggestion_ledger.py 两个模块内置 --selftest（本次已跑，均全部通过 ✅）。
影响：12.5k 行代码、31 条 API，任何阈值/数据结构改动都只能靠人工点页面验证；与「改完必 py_compile + 集成测试」的交付铁律存在落差。
建议：先补最小回归集 —— ① 全路由 GET 冒烟（本次探测脚本可直接固化为 tests/test_api_smoke.py）；② 快照字段契约（dashboard / sprite / gate_health 关键字段存在性）；③ 把本次体检的评分脚本做成 healthcheck.py 定期跑。
